Architecture

Five phases, end to end

From a raw CSV file to a live AI agent — each phase transforms the data and hands it to the next. Here is what happens at every step.

Data pipeline
01 Databricks
Data ingestion & transformation

The raw Inside Airbnb CSV (35,036 Sydney listings) is ingested into a Databricks workspace. PySpark jobs clean the data across three quality tiers: raw → silver → gold. Unity Catalog governs each table with schema enforcement and column-level lineage.

Inputlistings.csv (raw, 35,036 rows)
TransformNull handling, text normalisation, price parsing, duplicate removal
OutputGold-tier Delta table in Unity Catalog
02 pgvector
Embedding & vector indexing

Each listing's description is encoded into a 384-dimensional dense vector using BAAI/bge-small-en-v1.5. Vectors are stored in Supabase (PostgreSQL + pgvector). An HNSW index is built over the embedding column, enabling approximate nearest-neighbour search in under 100ms.

ModelBAAI/bge-small-en-v1.5 (33M params, local inference)
Dimensions384, L2-normalised for cosine similarity
IndexHNSW (m=16, ef_construction=64)
StorageSupabase: listings_embeddings + listings_structured tables
03 LangGraph
AI agent layer

A LangGraph ReAct agent orchestrates the entire query-to-answer loop. It reasons about which tools to call, inspects results, and iterates until it has enough information to synthesise a recommendation. The LLM is DeepSeek-Chat, accessed via OpenAI-compatible API.

Tool 1search_listings — semantic vector search, returns top-k matches
Tool 2get_listing_details — structured fetch (price, amenities, reviews)
LoopThought → Tool call → Observation → repeat until final answer
04 LangSmith
Guardrails & observability

A custom validation layer wraps every request and response. Inputs are screened for toxicity, off-topic queries, and competitor mentions before reaching the agent. Outputs are screened again before being returned. Every agent run produces a full LangSmith trace: latency, token counts, and a waterfall of tool calls.

Input checksToxicity, non-travel queries, competitor brand mentions
Output checksCompetitor mentions, policy violations
ObservabilityLangSmith project: travel-concierge (full waterfall traces)
05 Azure
Containerisation & deployment

The FastAPI app (API + frontend + model) is packaged into a Docker image. On every push to main, GitHub Actions builds and pushes the image to Azure Container Registry, then deploys a new revision to Azure Container Apps — achieving zero-downtime updates with a public HTTPS endpoint.

ContainerDocker multi-stage build, Python 3.11-slim base
RegistryAzure Container Registry
HostingAzure Container Apps (serverless, scale-to-zero)
CI/CDGitHub Actions deploy.yml — build → push → deploy on merge to main
Inside the agent loop

When a user sends a query, the ReAct agent follows this cycle. A single query typically completes in 7–10 seconds.

→

User query arrives at /chat

FastAPI receives the POST request. The guardrails layer validates the input — if blocked, a safe message is returned immediately.

🤔

Agent reasons about tools

DeepSeek-Chat reads the user message and the system prompt, then decides which tool to call first and with what arguments.

⌕

search_listings called

The query is encoded into a 384-d vector. Supabase executes an HNSW nearest-neighbour search and returns the top-k most semantically similar listings.

≡

get_listing_details called (1–3×)

For each promising match, the agent fetches structured data — price per night, amenities, superhost status, review score — from the listings_structured table.

✓

Final answer generated

The agent synthesises all observations into a recommendation. The output guardrail runs, then the response is returned to the user.
